## Step 0 · 合规红线

先判性质。**直接拒绝**：恶意脚本、破解付费保护、未授权攻击/入侵、越权爬虫、批量撞库、规避安全机制。

**不算违规**：自有代码/自有设备的逆向调试、自有数据迁移清理、授权范围内的渗透测试。

违规 → 说清原因、给合法替代、终止。合规 → 进 Step 1。

## 内置资源索引（三人行）

**lunyu 是流程编排层，且零外部技能依赖**——所有能力都内置在本包内，单独安装即可跑完整流水线，离线可用，不引用也不假设任何其他技能存在。

技术实现细节不属于流程范畴。遇到下面的场景，直接取用本包内置资源，不要重新造轮子：

| 场景 | 取用本包内置资源 | 触发时机 |
|---|---|---|
| 架构选型 / API 设计 / 规模适配 | `references/scale-adaptation.md` + Step 3 清单 | Step 3 方案设计 |
| 编码规范与反模式 | `references/anti-patterns.md` | Step 5 编码 |
| 测试金字塔 / 覆盖率 / 门禁分层 | `references/quality-gates.md` | Step 6 自测 |
| 发布门禁 / 灰度 / 回滚 | `references/git-release.md`（发布检查清单 + 回滚预案） | Step 8 发布 |
| 提交前密钥与调试残留扫描、依赖 SBOM | `scripts/preflight.py scan_deps` | Step 5 / Step 8 |
| 深度安全审计 | lunyu 只编排流程与门禁，扫描器（CodeQL / Semgrep 等）由用户环境自行安装 | Step 9 安全 |
| 漏洞验证假阳性 / 严重度分诊 | `templates/11-事故报告.md` + `references/quality-gates.md` 事故复盘 | Step 9 安全 |
| 前端 UI / 动画 / 媒体素材 | 不在流程范畴，交给用户自有设计工具链 | Step 5 编码 |

**边界规则**：
1. 用户提到「安全审计/漏洞/渗透」→ lunyu 做流程编排与门禁，深度扫描交给用户环境的专业扫描器，不重复实现
2. 用户提到「全栈/前后端/API」→ lunyu 管流程与验收口径，技术细节按通用工程常识 + 本包清单执行
3. 只做代码评审 → 直接用 `references/review-checklist.md` 的 7 维度 CR
4. 其他 → lunyu 全流程

## Step 1 · 需求澄清：对齐维度与追问要点

**先查经验库**（告诸往而知来者）：`python scripts/lessons.py search "<本次需求关键词>"`。
同类场景踩过的坑、验证过的结论会先摆出来，避免重复交学费。检索到的经验**参考不盲信**，技术会变，关键决策前复核。

**再扫目录**：已有代码库就先读结构、依赖、README。能从代码里看出来的，不要再问人。

必须对齐的维度（能推断的自行推断，标注「已推断」，不要逐条盘问）：

- 业务目标 / 解决什么问题
- 语言 / 框架 / 运行环境（含版本）
- 使用场景：个人 demo / 内部工具 / 生产服务 ← **决定后面所有环节的严格度**
- 核心功能清单
- 数据持久化需求
- 性能、并发、兼容性约束
- 交付形态：CLI / Web / API / GUI / 库
- 工程标识：工程根目录**绝对路径（含盘符）** / 根目录名 / 包名 / 命名空间（能推断则推断，标注「已推断」；确认即锁死，禁止中途改名、禁止换盘符、禁止换根目录——C 盘 D 盘乱跳属红线）
- 安全、权限、日志要求
- 版本管理：是否打 tag、是否要能回滚
- 是否启用缺陷台账

> 缺的信息**一次问完**，别挤牙膏式追问三轮。够开工就走，不为流程完美而空转。

**敏而好学，不耻下问**：上面说「能推断就推断」，反对的是**逐条盘问**，不是鼓励**硬猜**。
该问就问——尤其这几类**猜错代价极高**的：业务规则口径、金额与计费、权限与数据归属、对外接口契约、合规要求。
标「已推断」是给别人复核的机会，不是给自己硬猜的借口：**推断错了要认，不许把推断包装成确认。**

## Step 2 · 范围评审与变更控制

## Step 2 · 名正言顺：范围评审

产出需求确认单，必须写清 In Scope / Out of Scope / 验收标准 / 版本基线（基于哪个分支哪个版本开工）。

Out of Scope 是防范围蔓延的闸门，**必须写**，哪怕只一条。「这次不做」写下来，比「以后再说」有用一百倍。

### 变更控制（需求中途变了怎么办）

需求确认单不是一次性文件。中途变更**必须走变更流程**，不能口头一说了事：

1. **先判定是「变更」还是「澄清」** —— 澄清是把它说清楚（不改范围），变更是改范围。判据与对照表见 `references/scope-change.md`
2. **分级**：小改（不影响工期）/ 中改（影响工期不影响架构）/ 大改（影响架构或推翻已有工作）
3. **按级处理**：小改记录即可；中改要重估工期并确认；**大改必须重走本 Step（重新出需求确认单）**
4. **必须留痕**：改了什么、为什么、谁批的、影响评估、是否要重走确认

**红线**：口头变更一律不算数；未做影响评估不许开工；大改不重走确认单 = G1 门禁形同虚设。

**改名换包名算大改**：工程标识在需求确认单确认即锁死，**中途改名换包名一律视为范围大改**——必须重走 Step 2 重新出需求确认单，并专项评估对依赖引用、CI 配置、发布产物（安装包名 / bundle id / artifact 坐标）、已发布版本兼容性的连锁影响。流水线重复执行不会重新生成工程标识。

## Step 3 · 技术方案：取舍与过度设计

必须覆盖：整体架构、模块拆分与职责、数据流/接口定义、存储方案、异常与容错、依赖清单、**设计取舍（为什么不选其他方案）**、Git 分支规划（feature 分支名 + 目标合入分支）。

取舍说明是这份文档唯一的真正价值。只列技术栈不写为什么不用别的，等于没做设计。

**再，斯可矣**：想两次就够——选定一个方案、说清为什么不选另一个，就该动手了。
继续挖第三个、第四个方案是**分析瘫痪**，不是严谨。方案设计的产出是「一个决定」，不是「所有可能性的清单」。

**不过度设计**：不为假想的将来预留扩展点，不做当前规模用不上的抽象层，不引入「以后可能要」的依赖。
判断标准很简单：**这个抽象/扩展点，是现在的需求真的要求，还是我在为想象中的需求买单？**

规模适配：demo 只写架构 + 接口 + 依赖三节；生产服务全节齐全。

## Step 4 · 开源预研：调研维度

调研维度：

- 有无成熟库/组件可复用（优先官方文档与 GitHub 仓库本体）
- 维护活跃度：最近提交、issue 响应、star 趋势
- License：商用必查（GPL/AGPL 传染性、Apache-2.0 专利条款）
- 可借鉴的设计思路
- 已知坑与反模式

**硬约束**：吸收思路独立实现，禁止整段复制源码。无匹配方案就明写【无适配开源参考，自主实现】，别为交差硬凑一个不相关的库。

**众好之，必察焉**：star 高、大家都在推的，**也要自己跑一遍再下结论**。
README 写得漂亮但装不上、依赖冲突、License 另有陷阱、文档里的 API 实际已废弃——这些**只有跑起来才知道**。
最低要求：能装就装一次跑个最小示例；确实装不了就明写【未实测，仅纸面调研】，不许含糊过去。

**学而不思则罔**：调研完必须**回灌技术方案**，不是交一份报告就结束。
调研得出「这个库不合适 / 有更好的做法 / 有现成轮子」→ 回去改 Step 3 的方案。**方案要跟着调研结果变。**
学归学、做归做，调研报告就是白写的。

## Step 5 · 编码要求与 Git 分支


编码要求：

- 命名清晰，结构分层
- 参数校验、异常捕获、关键路径日志

## Step 6 · 测试分层与分支流转

### 6.1 TDD 红绿重构（新功能/缺陷修复必走）

**先写失败测试，再写实现**。三循环：

1. **红**：写能复现需求/bug 的测试，跑它，**确认失败**（红）——测试通过说明这个测试根本没测到东西
2. **绿**：写最小实现让测试通过，**不过度实现**（只做测试要求的）
3. **重构**：绿灯保护下清理代码（去重、改命名、拆函数），保持绿灯

每个循环只做一个功能点。**不是"写完再补测试"——那叫自我安慰。**

### 6.2 测试分层（不要只有单测）

| 层 | 覆盖什么 | 数量级 | 跑多快 |
|---|---|---|---|
| 单元测试 | 函数/类的逻辑与边界 | 最多 | 毫秒，每次改都跑 |
| 集成测试 | 模块间协作、DB/缓存真实读写 | 中等 | 秒级，push 前跑 |
| E2E / 冒烟 | 关键用户路径端到端 | 最少 | 分钟级，合并前跑 |


**边界优先**：空值、空数组、超长输入、并发、超时、权限不足。主流程谁都会测，缺陷都在边界。

**岁寒，然后知松柏之后凋**：跑得顺不算数，**条件恶劣时才见真章**。上面的边界只是入门，
生产服务还必须过一遍「恶劣条件」：依赖挂掉/超时是否真降级、磁盘写满、大数据量、弱网断网、
时钟回拨、重试风暴与幂等失效、token 过期/权限被拒、进程被杀后能否恢复。
完整清单见 `references/extreme-conditions.md`。**没实测过的降级路径，等于没有降级。**

### 6.3 实际运行

按语言配套单测（pytest / jest / unittest / JUnit）。**实际运行，贴真实输出**——不许写「测试应通过」。

CI 配置：`preflight.py --run` + 单测 + 覆盖率报告，全绿才算过。

分支：全通过 → Step 7；有缺陷 → 回 Step 5 修。

### 6.5 系统化调试（修 bug 必走四步）

遇到 bug / 异常，**不许上来就试改**：

1. **确定性复现**：找到能**稳定**复现的最小步骤（环境/数据/操作序列）。复现不了先解决复现——**复现不了的 bug 是玄学，不是工程**
2. **假设根因**：列出可能根因，按可能性排序，**写下来**
3. **最小测试证伪**：写最小测试验证最可能的假设，**证伪而非证实**——证实容易自欺，证伪才逼你排除错误路径
4. **只修根因**：修被证实的根因，**不顺手改别的**、不加防御性补丁掩盖症状

**症状 ≠ 根因**：报错行往往不是出错行。`try-catch` 吞异常、加 `!== null` 让测试过，都是掩盖症状——**掩盖的 bug 会以更贵的方式再回来**。

## Step 7 · PR + Code Review 细则

## Step 7 · 见贤思齐：PR + Code Review

PR 描述必含：需求背景、改动范围、自测情况、关联版本基线、关联缺陷单号。

CR 按 `references/review-checklist.md` 逐维度过：正确性、边界、可读性、耦合、健壮性、规范、安全隐患。每条意见给**可执行改法**，不说「这里不太好」。

**君子和而不同**：提意见，但不强加。CR 对**代码**不对人——
说「这段在并发下会重复扣款」，不说「你怎么连并发都没考虑」。

每条意见**必须标是否阻断**：`阻断` / `建议` / `纯风格`。**纯风格类意见不阻断合并**，
否则 CR 会退化成风格霸凌，最后没人愿意被评审、也没人愿意提意见。
拿不准就写「建议，不阻断」，把决定权留给作者。

CR 新发现的问题同样登记，标记关联当前 PR。

**交付物**：PR/MR 描述文本 + `## 【交付物：CR评审意见单】`（模板 `templates/10-CR评审意见单.md`）
+ 更新后台账 → **G3 门禁**

**法语之言，改之为贵**：每条「必须修改」的意见登记进缺陷台账（标关联 PR），
**全部关闭才允许合并**。意见提了没人改，CR 就退化成了走过场。

## Step 9 · 风险维度、可观测性三支柱与发布策略

## Step 9 · 人无远虑：风险评估 + 可观测性

维度：适用边界、性能瓶颈、安全风险、运维成本、扩展限制、版本兼容性。分级【高风险】【中风险】【低风险】。

**同步校验台账**：跑 `python scripts/bug_ledger.py stats`，有未关闭 P0/P1 则整体标【高风险】，并写明放行理由。

### 可观测性三支柱（生产服务必做）

| 支柱 | 具体要求 | 最低标准 |
|---|---|---|
| **日志** | 分类 + trace_id + 结构化 | 已在 Step 5 落地 |
| **指标** | 关键路径 QPS / 延迟 P95 / 错误率 | 至少暴露一个 `/metrics` 或打点到现成 APM |
| **追踪** | 跨服务链路 | 单体可省，微服务必做 |

### 发布策略（不只是打 tag）

| 策略 | 适用 | 要点 |
|---|---|---|
| **Feature Flag** | 新功能不想一次全放 | 代码合了但开关关着，出问题关开关，不用回滚 |
| **灰度/金丝雀** | 有流量分层的服务 | 先 5% 流量，观察错误率和延迟再放量 |
| **蓝绿** | 可整机切换 | 新版本起来验证通过再切流量，回滚=切回去 |

**数据库变更单独管**：加字段可回滚，删字段/改类型不可回滚。**先加新字段双写 → 验证 → 再删旧字段**，分两次发布。一次性改表结构 = 回滚预案失效。

## Step 10 · 复盘板块明细

## Step 10 · 吾日三省：复盘沉淀

**分两种，不要混：**

### 10.1 常规迭代复盘（每轮必做）

固定三块，**必须具体**。「加强测试」是废话；「XX 边界场景未覆盖，因为设计时只想了 YY」才是复盘。

- ✅ **收获**：选型经验、调研所得、架构思路、规范实践
- ⚠️ **失误与改进**：需求盲区、方案漏洞、调研遗漏、自测缺失 + 具体规避办法
- 🐛 **缺陷根因**：逐条归类（需求问题/设计问题/编码疏漏/测试漏测）+ 改进措施

**复盘完必须沉淀**（否则下次还得再摔一次）：把本次的踩坑和结论逐条入经验库。

```bash
python scripts/lessons.py add --scene "<场景>" --problem "<错在哪>"   --solution "<正确做法>" --tags "<标签>" --kind 踩坑|结论|偏好|禁区|技巧
```

判断标准：**只要这次踩了坑、或者得出了一个"下次照做"的结论，就该入库**。复盘写了但没入库，等于没沉淀。

缺陷可以直接转成经验，不用手动重录：

```bash
python scripts/lessons.py add --from-bug BUG-0001      # 从已关闭缺陷生成经验
python scripts/lessons.py stale --days 180             # 哪些经验该复核了
python scripts/lessons.py add --global --scene "..."   # 存到全局库，跨项目复用
```

`--global` 存到 `~/.lunyu/lessons.json`，`search` 默认**本地 + 全局一起查**（本地优先）。
项目级经验放项目里，**通用教训放全局库**，换项目不再从零开始。

### 10.2 事故复盘（P0 故障后必做，无责模式）

出了 P0 就写事故报告，跟常规复盘**分开**。核心原则：**追流程漏洞，不追人**。追责的文化会让下一个人藏事故。

| 板块 | 内容 |
|---|---|
| **时间线** | 精确到分钟：何时发生、何时发现、何时定位、何时恢复 |
| **影响面** | 多少用户/订单/金额，持续多久 |
| **根因** | 直接原因 + **根本原因**（连问五个为什么，问到流程层） |
| **发现方式** | 告警主动发现 / 用户投诉 / 偶然看到 ← 这条最能暴露监控缺口 |
| **恢复过程** | 做了什么才好的，中间走了哪些弯路 |
| **改进项** | 每条带**负责人和截止时间**，分「已做/待做」 |

**关键指标**：MTTD（发现耗时）、MTTR（恢复耗时）。复盘的价值就是让这两个数字降下来。

**事故教训必须入经验库**——事故是最贵的学费，不入库存等于白交：

```bash
python scripts/lessons.py add --scene "<故障场景>" --problem "<根因>" \
  --solution "<根治办法>" --tags "事故,P0" --kind 禁区 --source "事故复盘"
```

改进项同时登记进缺陷台账（带负责人和截止时间），否则「待做」永远停在纸面上。

## Step 11 · 收尾选项、质量标准与已知未闭环

## Step 11 · 无可无不可：收尾

给用户选，不要自己猜：

1. 按 CR 意见/风险点重构，当前分支迭代新版本
2. 新增需求，新开 feature 分支
3. 导出全套交付包（需求单+方案+调研+源码+单测+PR+CR+台账+存档+CHANGELOG+风险+复盘）→ 导出时**用 `templates/08-交付清单.md` 逐项打勾**，防止漏交
4. 查台账 / 查指定 bug / 改缺陷状态
5. 查历史版本存档 / 要回滚指引
6. 新建独立缺陷工单（不绑当前迭代）
7. 结束，开启新需求

### 收尾质量标准（譬如为山，未成一篑）

堆到九成停下来，前面的功夫全白费——**最后 10% 才是决定成败的那一篑**。收尾前逐项确认：

| 检查项 | 标准 |
|---|---|
| 交付物齐不齐 | 用交付清单模板逐项打勾，**构建产物/安装包 + md5 不能少** |
| 质量动作做没做 | 自测实际跑过、`preflight.py` 扫过、缺陷已登记、版本基线已记录 |
| 已知问题说没说 | **必须显式列出已知未闭环项**（见下） |
| 能不能退回去 | 回滚命令明确、影响范围清楚、校验方式写明白 |
| 别人接得住吗 | 关键决策有据可查（取舍说明、经验库），不是只留下代码 |

### 过而不改，是谓过矣（已知未闭环必须声明）

**交付时必须显式列出「已知未闭环项」**：没修的缺陷、没做的检查、跳过的步骤、遗留的技术债——
每一项写清 **是什么 / 为什么这次不做 / 什么时候补 / 不补会怎样**。

发现问题不是错，**发现问题捂着不说才是错**。沉默的已知问题会变成下一个人的事故。

## 交付物落盘位置（`.lunyu/` 目录结构）

## 交付物落盘位置

过程产物统一写入项目根目录 `.lunyu/`，不要散在根目录：

> **根目录须显式锁死，禁止 CWD 漂移。** 运行任何 lunyu 脚本前，必须 `cd` 到项目根目录，或显式传 `--root <绝对路径>`；绝不依赖「当前工作目录」隐式定位。否则定时任务 / 换终端触发时，CWD 可能是 System32 之类，`.lunyu/` 会被写到错误位置，过程产物与状态全部错位（此坑真实踩过）。工程根目录绝对路径以需求确认单为准，确认后不再变动。

```
.lunyu/
├── bugs.json          # 缺陷台账（脚本管理，勿手改）
├── releases.json      # 版本存档（脚本管理，勿手改）
├── lessons.json       # 经验库（lessons.py 管理）
├── sbom.json          # 依赖清单 SBOM（preflight.py 生成）
├── CHANGELOG.md       # 变更日志
├── decisions/         # ADR 架构决策记录（adr.py 管理）
├── docs/              # 需求单/方案/调研/CR/风险/复盘
└── reports/           # 日报/周报/项目总结（report.py 生成）
```

另有一份**跨项目全局经验库**：`~/.lunyu/lessons.json`（`--global` 写入）。

## 多 AI / 多人协作一致性

不同 AI agent（或人）并行开发同一项目，最易踩三个坑：**版本基线漂移**（A 用三天前的源码，B 用今天的）、**互相覆盖**（两人同时改同一文件，后提交者覆盖前者）、**各存各的**（项目散落不同盘符 / 目录，谁也找不到最新那份）。纪律：

1. **唯一事实源**：源码只在 git 仓库，不在任何人的本地游离副本。lunyu 不替你"存"项目，所有 agent 都从同一仓库同一分支取。
2. **开工即同步**：任何 agent 动手前先 `git fetch` 并基于锁定分支最新 HEAD 建工作分支，禁止拿"手头碰巧有的那份旧代码"开工。
3. **责任区 + 独立分支**：并行时按文件 / 模块划责任区，各自 `feature/<模块>-<负责人>` 分支，互不踩踏；冲突靠 PR + CR 收敛，不靠谁后提交谁赢。
4. **落盘唯一**：呼应「工程根目录绝对路径（锁死）」——所有 agent 落到确认单指定的同一个绝对路径，不各存各的。

## 智能自进化（技能元进化）

lunyu 的自我改进闭环：运行 → 经验入库（lessons，标 `skill:true`）→ 复盘 / 被纠正时 evolve 提取 → 合并进 SKILL.md / references / templates → bump 版本。

- 任何「下次照做」的结论、反模式、用户纠正，先入经验库并标 `skill:true`
- `python scripts/evolve.py`：扫描 lessons（项目 + 全局），输出「建议上升为技能规则」清单（`.lunyu/evolution-proposals.md`）
- 候选经确认后合入技能定义；用户的纠正优先、最高优先级
