# 收到评审意见怎么办

> 对应 Superpowers 的 `receiving-code-review`。
> 论语出处：《论语·先进》「法语之言，能无从乎？改之为贵」——
> 别人说得对，能不听吗？改了才可贵。**前提是「说得对」**——
> 评审意见不等于正确答案，先验证，再决定改不改。

## 铁律：先验证，再回应

收到意见第一件事不是改代码，是**验证这条意见成不成立**。

```
收到意见
  ↓
1. 复现：按对方描述的路径，真的会发生吗？
  ↓
2. 读代码：那行代码前后文是什么？有没有他没看到的保护逻辑？
  ↓
3. 判断：这是【必须改】、【可以改】还是【不成立】？
  ↓
4. 回应：改 / 反驳（带证据）/ 需要讨论
```

**禁止「你说得对，我改」**。这是 AI 最常见也最有害的坏毛病——
评审者说的不一定对，无脑全盘接受会把正确的代码改错，
而且让评审者误以为自己那条意见有价值。

## 三种回应方式

### 1. 接受 —— 说得对，改

验证成立，就改。改完要说明改了什么：

```
已改。`pay.py:88` 的 `items[0]` 在空数组时会抛异常，
按建议加了长度判断，并补了空数组的测试用例。
```

不要只说「已修复」。**说清改了哪、为什么这样改、有没有补测试。**

### 2. 反驳 —— 说清楚为什么不对

验证不成立，就反驳，**必须带证据**：

```
这条不成立。`pay.py:88` 上面第 85 行已经做了 `require_non_empty(items)`
校验，空数组走不到这里。我加了个测试用例证明：
空数组在第 85 行就抛了，88 行确实不可达。
```

反驳的三种常见情形：

- **对方没看到保护逻辑** —— 上游已经校验/已经在事务里/已经有默认值
- **对方的判断基于过时代码** —— 他看的是旧版本，现在改过了
- **风格偏好被当成规范** —— 他喜欢那种写法，但项目约定不是那样

**反驳不是抬杠**。带上代码位置和证明，对方能立刻判断谁对。

### 3. 需要讨论 —— 各有道理，得拍板

技术上都说得通，但影响取舍（性能 vs 可读性、简单 vs 扩展性）：

```
两种写法都可以：A 方案快但难读，B 方案清晰但多一次遍历。
当前这个接口 QPS 不高，我倾向 B。如果你认为性能更重要我改 A，
但想先确认一下这个接口的实际量级。
```

## 常见误报（评审意见里的错误类型）

| 误报类型 | 特征 | 怎么验证 |
|---|---|---|
| **没看全上下文** | 说第 N 行有问题，但第 N-3 行已经处理了 | 往上读 20 行，看有没有前置校验 |
| **基于过时版本** | 引用的行号/代码跟你本地不一样 | 让他确认 commit sha |
| **风格当规范** | 「我觉得应该……」没有依据 | 查项目约定（lint 规则、现有代码惯例） |
| **过度防御** | 要求处理不可能发生的情况 | 问：什么场景下会触发？能触发吗？ |
| **转移话题** | 意见跟这次改动无关 | 指出「这是既有问题，建议单独开单」 |

## 遇到「必须改」但你认为不用改

**按流程走**：先改，同时把你的理由写清楚，让最终决策者判断。
不要在 CR 里僵持——CR 不是辩论赛，卡住的是整个交付。

改完留一句：

```
按意见改了（加了兜底）。补充一句：这个分支在当前调用链下走不到，
加兜底是为防御后续改动。如果认为属于过度防御，我可以撤掉。
```

## 批量意见的处理顺序

1. **先分类**：正确性 / 安全 > 可维护性 > 风格
2. **先改正确性**，风格类可以一次批量处理
3. **每条都要有回应**，不能改了三条、沉默五条
4. **改完全部跑一遍测试**，不要改一条跑一条（除非是定位问题）

## 反模式

- **表演性同意** —— 「说得对，马上改」，其实没验证过
- **选择性回应** —— 好改的改了，难改的装没看见
- **情绪化反驳** —— 「这个没问题」「一直都是这么写的」，不给证据
- **批量无脑接受** —— robot 式全盘照改，把对的改错
- **改完不跑测试** —— 改了五条意见，一条都没验证
