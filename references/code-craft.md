# 代码工艺 · 写好代码的判断依据

> 用途：Step 5 编码、Step 6 自测、Step 7 CR 的判断依据。
> 这一份回答的是「**这段代码写得好不好**」，不是「流程走完没有」。
>
> 完整流程看 SKILL.md；本文件只看代码本身的质量。
> 机器能查的部分用 `python scripts/codecraft.py`，人/AI 判断的部分看本文。

---

## 一、通用工艺（不分语言都成立）

### 命名

- 名字要能回答「它是什么 / 它干什么」。`d`、`tmp`、`data`、`handle` 一律不合格
- 布尔量用 `is_` / `has_` / `can_` / `should_` 开头
- 函数用动词开头（动词+宾语）：`calc_refund()` 而不是 `refund_calc()`
- 同一个概念全项目一个名字。别一会儿 `user` 一会儿 `account` 一会儿 `member`

### 函数

- **一个函数只做一件事**。判断标准：能用一句话说清它干什么，中间没有「然后」
- 超过 30 行要警惕，超过 60 行基本都有问题（`codecraft.py` 会报）
- 参数超过 4 个，考虑引入参数对象
- **不要布尔参数**——`send(msg, true)` 谁看得懂？拆成两个函数：`send_now()` / `send_later()`

### 错误处理

- **不要吞异常**。`except: pass` 是最坏的习惯，出问题时连线索都没有
- 不要「静默失败」——函数返回 `None` 却不告诉调用方为什么，等于把问题往后推
- 错误信息要说清三件事：**什么东西、出了什么问题、当时的关键值**
  - 坏：`"操作失败"`
  - 好：`"退款失败：订单 20261030001 状态已为已退款，不能重复退款"`
- 可恢复的错误返回错误，不可恢复的抛异常。**不要用返回码假装没出错**

### 注释

- 注释写「**为什么**」，不写「做了什么」。`i += 1  # i 加一` 是废话
- 代码能自解释就别加注释；加了注释说明代码不够清楚，优先改代码
- **注释掉的代码直接删**，不要留在那「万一以后要用」——git 里有历史
- TODO 要带责任人和时间：`# TODO(张三, 2026-11-15): 迁移到新接口`

### 边界

- 所有外部输入都要校验：空值、超长、超范围、类型不符、重复
- 集合操作先判空/越界
- 除法先判零
- 涉及钱、库存、计数的，先想清楚并发下会不会错

## 二、语言最佳实践（挑最容易错的写）

### Python

- 用 `with` 管资源，别手动 `close()`
- 可变对象不做默认参数：`def f(x, items=[])` 是经典 bug
- 用 `logging` 不用 `print`
- 类型注解能加就加，比注释管用
- 别用 `except Exception` 一把抓，明确捕获具体异常

### JavaScript / TypeScript

- 一律 `===`，不用 `==`
- 异步全链路 `async/await`，**不允许漏 `await`**（漏了是静默 bug）
- `Promise` 必须有 `catch`，否则错误静默丢失
- 不用 `any` 逃避类型；实在要就用 `unknown` 再收窄
- 数组遍历优先 `map/filter/reduce`，少写 `for` + `push`

### Java / Kotlin（含 Android / 车机）

- 空安全：Kotlin 用 `?` 明确可空，别用 `!!`
- 主线程不做网络/数据库/大文件 IO
- Android 上下文别存静态引用（内存泄漏）
- 广播/监听注册与注销必须成对
- **车机 / 定制 ROM**：静态广播可能被裁剪，关键通道要有动态注册兜底

### Go

- error 必须处理，`_` 丢掉 error 要写注释说明为什么
- 不要 `panic` 当错误处理
- goroutine 要有退出机制，别泄漏

### Shell

- 开头写 `set -euo pipefail`
- 变量引用一律加引号 `"$var"`
- 路径含空格必须引号包裹

## 三、代码异味清单（CR 逐条过）

| # | 异味 | 表现 | 怎么改 |
|---|---|---|---|
| 1 | **重复代码** | 相同或几乎相同的代码块出现 2 次以上 | 提炼函数 / 提炼公共模块。`codecraft.py` 会自动报 |
| 2 | **过长函数** | 超过 60 行，或一屏看不完 | 按职责提炼函数 |
| 3 | **嵌套过深** | if/for 嵌套 4 层以上 | 卫语句提前返回、分解条件 |
| 4 | **过长参数列表** | 超过 4 个参数 | 引入参数对象 |
| 5 | **散弹式修改** | 改一个需求要动十几个文件 | 把相关逻辑收拢到一处 |
| 6 | **魔法值** | 代码里直接写 `7`、`"admin"`、`3.14` | 提为常量并命名 |
| 7 | **死代码** | 定义了没人用的函数/类/导出 | 删。git 里有历史（`codecraft.py` 会报） |
| 8 | **注释复述代码** | 注释说的是代码本身 | 删注释或改写成「为什么」 |
| 9 | **注释掉的代码块** | 大段被注释的代码 | 删 |
| 10 | **布尔参数** | `f(x, true)` | 拆成两个语义明确的函数 |
| 11 | **数据泥团** | 几个参数总是一起出现（如 `name, phone, addr`） | 提取成对象 |
| 12 | **过度防御** | 到处判空判类型，八成永远不触发 | 在边界统一校验，内部相信契约 |

## 四、重构手法对照（对症下药）

| 症状 | 手法 |
|---|---|
| 函数太长 | 提炼函数（Extract Function） |
| 一段代码就需要一行注释解释 | 同上，函数名就是注释 |
| 表达式太复杂 | 引入解释性变量（Extract Variable） |
| 临时变量到处传 | 以查询取代临时变量 |
| 函数用了别的类的数据比自己的多 | 搬移函数（Move Function） |
| 参数总是成组出现 | 引入参数对象 |
| 复杂条件判断 | 分解条件表达式 / 合并条件 |
| 嵌套 if 太多 | 卫语句（提前 return） |
| 同一段逻辑复制多份 | 提炼函数 + 提公共模块 |
| 大量 switch/if-else 按类型分支 | 以多态/表驱动取代条件 |

**重构的前提是有测试。** 没测试先补测试，别裸重构——这是「欲速则不达」。

## 五、安全反模式（CR 必查）

| 类型 | 表现 | 正确做法 |
|---|---|---|
| **注入** | 字符串拼接 SQL / 命令 `/ 反序列化` | 参数化查询 / 白名单校验 |
| **XSS** | 用户输入直接渲染到页面 | 转义输出 / 用框架的自动转义 |
| **越权** | 只判断「登录了没」，不判断「是不是他的」 | **每次数据访问校验归属**（水平越权是最常见也最致命的） |
| **敏感信息** | 密码明文存、token 进日志、身份证/手机号打日志未脱敏 | 加密存储 + 日志脱敏（`logkit.py` 生成的脱敏函数） |
| **密钥硬编码** | 代码里写 AK/SK/token | 环境变量。`preflight.py` 会扫 |
| **不安全的默认值** | 默认全开权限、默认关闭校验 | 默认最小权限 |
| **依赖漏洞** | 用了有已知 CVE / 已弃维护的包 | `preflight.py` 依赖体检 |

## 六、性能反模式（CR 必查）

| 类型 | 表现 | 正确做法 |
|---|---|---|
| **N+1 查询** | 循环里逐条查库 | 批量查询 + 内存组装 |
| **嵌套循环** | 双层遍历大数据集 | 用 map/dict 索引 |
| **循环内 IO** | 循环里发请求 / 读文件 / 查库 | 提到循环外批量做 |
| **全表扫描** | 查询条件没走索引 | 加索引 / 改查询条件 |
| **全量加载** | 一次性 `SELECT *` 拉全表到内存 | 分页 / 流式 |
| **循环内字符串拼接** | `s += x` 在循环里 | 用 join / builder |
| **重复计算** | 循环里反复算同一个值 | 提到循环外 |
| **同步阻塞主流程** | 非关键路径串行等待 | 异步 / 并行 |

性能不是「感觉慢」才优化。上面这几条是**写法问题**，看到了就该改，不用等压测。

## 七、AI 写代码特有的坏习惯（重点）

这几条是 AI 生成代码的通病，CR 时重点盯：

1. **造轮子** —— 项目里已有工具函数，又写了一遍。动手前先搜有没有现成的
2. **堆防御代码** —— 到处判空判类型，八成分支永远走不到，代码臃肿难读
3. **过度抽象** —— 三个参数的函数非要套个设计模式的壳
4. **改一半就走** —— 留 TODO、留未实现分支、留重复定义，说「剩下的你自己补」
5. **死代码** —— 写完没用上的函数/导入/变量，堆在那
6. **凭印象调 API** —— 没读源码就按记忆写，参数名、返回结构全是猜的
7. **注释复述代码** —— 每一行加个注释，看起来很努力，其实全是废话
8. **只测正常路径** —— 测试只覆盖 happy path，边界和异常一概不管

> 前 5 条 `codecraft.py` 能机器查，后 3 条靠 CR 人/AI 盯。

## 八、CR 时的自检顺序（照着过一遍）

1. **能跑吗** —— 实际跑过没有？（不是「应该能跑」）
2. **对吗** —— 边界、异常、并发下还对吗？
3. **安全吗** —— 越权、注入、敏感信息、密钥
4. **快吗** —— N+1、嵌套循环、循环内 IO
5. **好读吗** —— 命名、函数长度、嵌套深度、注释
6. **有重复吗** —— 有没有再造轮子 / 复制粘贴
7. **有测试吗** —— 正常/边界/异常/并发，改的是存量代码吗（→ `impact.py`）
8. **目标环境过了吗** —— 真机 / 生产环境实测（→ `16-目标环境验证清单.md`）

---

> 「文质彬彬，然后君子」——功能（质）和可读性（文）要配得上。
> 只堆功能不看可读性，或只重包装不重功能，都算不上好代码。
