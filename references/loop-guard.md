# 失控自检：循环、反复失败与主动报告

> 《论语·学而》「过则勿惮改」——错了别怕改，但得**先承认错了、说清错在哪**。
> 《论语·卫灵公》「工欲善其事，必先利其器」——先有能看见自己行为的工具，才谈得上自律。

## 为什么需要这一条

AI 执行任务最常见的翻车不是「不会做」，是**不会停**：

- 同一条命令连跑五遍，每次都 `ModuleNotFoundError`，还觉得「再试一次说不定就好了」
- 同一个文件改八遍，测试每次以同一种方式红，注意力全在「换个写法」，没回头看失败栈第一行
- 网络断了硬重试十几轮，把 token 烧光，用户还以为进展顺利
- 卡住之后开始**编**：把「还在调」说成「基本完成」，把没跑过的验证说成「应该没问题」

前三条浪费成本，第四条摧毁信任。所以这条规则压过流程里所有「继续推进」的要求。

## 一、硬规则：出现以下任一情形，立即停

**当出现下列任一信号时，按以下步骤执行：停止重试 → 跑检测 → 输出诊断报告 → 等用户决策。**

| # | 判据 | 为什么必须停 |
|---|---|---|
| 1 | 同一动作/命令连续重复 **3 次** | 前两次没变，第三次也不会变。重试不是进展 |
| 2 | 同一错误出现 **3 次**（哪怕换了命令） | 说明是同一个根因，换入口没用 |
| 3 | 连续失败 **3 次** | 前提假设已经不成立，继续只是叠加噪音 |
| 4 | 最近 **6 步**没有任何一次成功 | 空转，方向或方法有问题 |
| 5 | 累计动作数达到预算（默认 **40**） | 防止长任务悄悄滑成无限循环 |
| 6 | 自己开始说「再试一次」「换个方式」但做法实质相同 | 语言在换，行为没换，属于伪装的重试 |

**停下来的同时必须做三件事**：

1. **主动报告**——不要闷头继续，不要等用户问「做到哪了」。直接说清楚：卡在哪、证据是什么
2. **分析原因**——给「可能原因 + 判断依据 + 怎么验证」，**验不了就明说验不了**，不许编一个听起来专业的原因
3. **给出决策点**——是继续修、换方案、还是先搁置；哪些外部条件（凭据/网络/目标环境）需要用户来提供

> 完整命令见 `references/script-index.md`；报告模板见 `templates/18-失控诊断报告.md`。

## 二、执行方式

```bash
# 每完成一步动作记一笔（失败时 --error 传完整原文，别只写「失败了」）
python scripts/loop_guard.py log --action "跑单测" --status fail \
    --error "ModuleNotFoundError: No module named foo" --signature "pytest tests/"

# 检测（退出码 1 = 必须停）
python scripts/loop_guard.py check
python scripts/loop_guard.py check --json

# 生成给人看的诊断报告
python scripts/loop_guard.py report --out .lunyu/失控报告.md

# 新任务开工先清轨迹 / 调预算
python scripts/loop_guard.py reset --yes
python scripts/loop_guard.py budget --max 30
```

`log` 的 `--signature` 是给「同一个命令的不同措辞」用的：写 `pytest tests/` 后，
不管描述写成「跑单测」还是「执行测试」，都会被认成同一个动作。

## 三、原因分类学（附验证方法，不下断言）

脚本按错误文本里的信号词给出**候选**，每条都带「怎么验证」。命中信号 ≠ 结论，
验证不成就划掉，补新证据再立假设。

| 类别 | 典型信号 | 最该先做的验证 |
|---|---|---|
| 环境漂移 / 依赖缺失 | `ModuleNotFoundError` / `command not found` | `env_check.py verify` 对比 `.lunyu/env.lock` |
| 路径 / 目标定位错 | `FileNotFoundError` / `not a git repository` | `locate.py --keyword <目标>` 正向定位 |
| 上下文失效 | `Connection was reset` / `401` / `timeout` | 手工复现最小请求，确认凭据/服务状态 |
| 根因假设错 | `AssertionError` / 同一处反复改仍红 | 读失败栈第一行自己代码 + `impact.py --file` |
| 没有验收点 | 「再试」「换个方式」反复出现 | `plan.py list` 看当前任务验收点是否为空 |
| 任务没拆 | `conflict` / `revert` / 多文件来回跳 | 看 `git status` 改动面，用 `worktree.py` 隔离 |
| **证据不足** | 错误文本太短或没有 | 补齐原文；如实写「原因未确定」，**不要编** |

## 四、脱困动作（按顺序，别跳步）

1. **读完整错误**，不是只看最后一行。很多「反复失败」的答案就在栈的第一行
2. **验证前提**：环境、路径、权限、网络，是不是和开工时一样（`env_check.py verify`）
3. **划掉已否决假设**，写进 `HANDOVER.md`——不然换个会话又从同一条错路开始
4. **补验收点**：说不清「什么算做完」时，先 `plan.py set-acceptance`，别继续微调
5. **缩小范围**：一次只改一个变量。同时改三处，失败了不知道是哪处的锅
6. **换通道**：网络/凭据类阻塞换离线路径或直接上报，不靠重试碰运气
7. **如实上报**：现象、证据、已排除项、需要用户决策的点，四项齐全

## 五、反模式（见到就停）

| 反模式 | 为什么有害 |
|---|---|
| 同一命令静默重试，不告诉用户 | 用户以为在推进，实际在原地 |
| 换个措辞重试同一件事 | 语言变了行为没变，循环检测能抓到 |
| 改代码绕过缺失依赖 | 把环境问题伪装成代码问题，越修越歪 |
| 把「还在调」写成「已完成」 | 直接违反「知之为知之」，一句话毁掉全部可信度 |
| 编一个听起来专业的原因 | 比承认「不知道」更糟，会把排查带向错方向 |
| 报错文本只记「失败了」 | 证据没了，事后谁都没法归因 |

## 六、与流水线的关系

- 这是**贯穿全程的护栏**，不是第 13 步。任何 Step 里触发都要停
- 与 `verify.py` 的分工：`verify.py` 管「交付前有没有证据」，`loop_guard.py` 管「执行过程中有没有卡死」
- 与 `evolve.py` 的闭环：每次脱困后的正确归因，值得在 Step 10 复盘时沉淀进经验库
- 快速通道也不能省这条——省的是文档篇幅，不是停下来报告的动作
