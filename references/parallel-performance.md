# 并行协作与性能

> 两部分：一是多任务/多 AI 怎么并行不打架，二是性能怎么改才不白改。
> 论语出处：《论语·颜渊》「君子成人之美」——协作篇；
> 《论语·子罕》「欲速则不达」——性能篇（凭感觉优化就是图快）。

---

# 一、并行协作：多个任务 / 多个 AI 同时推进

## 什么时候需要隔离

| 场景 | 风险 | 做法 |
|---|---|---|
| 一个需求改到一半，插进来急活 | 改一半的文件被覆盖 | `worktree.py create` 开独立目录 |
| **多个 AI / 多个会话同时改同一仓库** | 互相覆盖，且都不知情 | **必须隔离**，这是头号解药 |
| 想看看别的分支长什么样 | 切分支打断当前工作 | worktree，不用切 |
| 长跑任务（大重构）和日常改动并行 | 互相污染 | 各占一个 worktree |

## 用法

```bash
python scripts/worktree.py create feat/pay-refactor --from main
# 输出路径，进去干活
cd <路径>
python scripts/worktree.py list        # 看有几个工作区、干不干净
python scripts/worktree.py remove feat/pay-refactor   # 干完移除
python scripts/worktree.py remove feat/pay-refactor --drop-branch   # 连分支一起删
```

**要点**：worktree 与主工作区共用同一份 `.git`（提交互通），
但**文件完全独立**——在隔离区改东西不会动到主工作区。

## 派发子任务的原则

拆任务之前先问：**这两件事真的独立吗？**

- **独立**（改不同模块、不共享状态）→ 可以并行派发
- **有依赖**（B 要等 A 的接口定下来）→ 串行，别并行
- **共享同一个文件** → 绝对不要并行，会互相覆盖

派发时每个子任务必须带三样东西，缺一样就别派：

1. **明确边界**：改哪些文件，不碰哪些文件
2. **验收点**：怎么算做完（可验证，不是「做好」）
3. **上下文**：给足背景，别让他自己去猜（把相关文件路径给他，不是让他找）

> 用 `plan.py` 拆任务、`impact.py` 确认影响面，再派发。

## 多 AI 协作的三条硬纪律

1. **同一时间同一文件只能有一个 AI 在改** —— 用 worktree 隔离，或者串行
2. **每个 AI 开工先读 `HANDOVER.md`，收尾更新它** —— 唯一跨会话的上下文
3. **每个 AI 动手前跑 `env_check.py verify`** —— 环境对不上，改出来的东西对不上

# 二、性能：先测量，再改

## 铁律：没有测量结果，不许优化

凭感觉优化是通病，而且危害比不优化更大：

- **改的不是瓶颈** —— 你猜是 N+1 查询，实际是序列化，改完没变化
- **改完更难读** —— 为了 0.1ms 把代码写成天书
- **引入新 bug** —— 缓存没失效、并发没保护

**性能优化的唯一正确顺序**：

```
1. 测量：找到真正的瓶颈（profile / 埋点 / 日志耗时）
2. 定位：确认是这段代码（不是网络、不是数据库、不是客户端）
3. 改：只改瓶颈处
4. 复测：拿数据证明快了（同一组输入，前后对比）
5. 记录：改了什么、快了多少、有没有副作用
```

**没有第 1 步和第 4 步的，不算优化，算瞎改。**

## 怎么测量（没有专业工具也能做）

| 手段 | 适用 | 怎么做 |
|---|---|---|
| **分段计时** | 任何语言 | 在关键步骤打点，输出每段耗时 |
| **重复跑 N 次取均值** | 微基准 | 单次耗时不准（JIT、缓存），跑 100 次 |
| **日志里的耗时** | 线上 | 用 logkit 生成的 `timed` 装饰器自动记 |
| **数据库慢查询** | SQL 相关 | 打开慢查询日志，别猜哪条慢 |
| **浏览器 DevTools** | 前端 | Network 面板看谁慢，Performance 面板看主线程 |

**最小可用的测量**：在要优化的函数前后加计时，跑真实数据量，看耗时分布。

```python
# 别用单次 time.time() 判断快慢，跑够次数
import time
def bench(fn, n=100):
    ts = []
    for _ in range(n):
        t0 = time.perf_counter()
        fn()
        ts.append(time.perf_counter() - t0)
    ts.sort()
    return {"p50": ts[n//2], "p95": ts[int(n*0.95)], "avg": sum(ts)/n}
```

看 **p95 不看 avg** —— 平均值会被偶尔的快掩盖掉长尾。

## 常见的真瓶颈（按出现频率）

1. **N+1 查询** —— 循环里查库，头号杀手
2. **循环内的 IO** —— 读文件、发 HTTP、写日志
3. **缺索引 / 全表扫描** —— 数据量小的时候看不出来
4. **一次捞全量** —— 没有分页，数据量涨了就崩
5. **重复计算** —— 同样的结果在循环里算 N 遍
6. **序列化/反序列化** —— 大对象的 JSON 转换
7. **锁竞争** —— 并发上不去，不是 CPU 不够

## 不要做的优化

- **为 0.1ms 牺牲可读性** —— 除非在热路径上跑百万次
- **没有数据支撑的「优化」** —— 觉得这样更快，测都没测
- **过早引入缓存** —— 缓存带来失效问题和一致性问题，先确认真的需要
- **改了不改回** —— 优化完发现没效果，要敢于回退

## 反模式

- 「这里应该会慢，我先优化一下」 —— **应该**不是数据
- 改完全局跑一次觉得「好像快了」 —— 感觉不是证据
- 只测优化后的耗时，没测优化前的 —— 没有基线等于没测
- 用空数据/小数据量测性能 —— 性能测试必须用生产量级的数据
