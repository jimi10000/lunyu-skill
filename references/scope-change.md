# 范围变更控制

> **君子之于天下也，无适也，无莫也，义之与比。** ——《论语·里仁》

不预设立场，只以「是否合宜」为准。变更不可怕，**没有规则的变更**才可怕。
需求中途变更本身不是问题，问题在于：改了没人记、工期没人认、做完了没人知道范围已经变了。

## 第一步：判定「变更」还是「澄清」

### 判定三问

| 问题 | 答「是」→ 倾向 |
|---|---|
| 已确认的需求文档里，这件事有没有写清楚？ | 写清楚了 → 变更 |
| 按现有约定，能否唯一确定该怎么做？ | 不能唯一确定 → 澄清 |
| 做出来之后，已交付的部分要不要改？ | 要改 → 变更 |

### 对照表

| 说法 | 判定 | 理由 |
|---|---|---|
| 「这个按钮放左上角还是右上角？」 | 澄清 | 需求未细述，不影响已完成工作 |
| 「这里的错误提示文案改成 XX」 | 澄清 | 单点调整，无工期影响 |
| 「导出再加个 Excel 格式」 | 变更（小） | 新增了原需求没有的功能点 |
| 「只要登录就行，不用做权限分级了」 | 变更（中） | 减少范围也是变更，工期要重算 |
| 「数据要从 MySQL 换成 TiDB」 | 变更（大） | 影响架构，推翻既有工作 |
| 「之前那个流程不用了，改成新的」 | 变更（大） | 推翻已交付工作 |
| 「顺便把这个也加一下吧」 | 变更 | **没有「顺便」，一切新增都是变更** |

**判定不清时，一律按变更处理。** 低估的代价远大于多走一次流程。

## 第二步：分级

| 级别 | 定义 | 典型例子 | 谁批 | 重走需求确认 | 重出方案 | 工期 |
|---|---|---|---|---|---|---|
| **小改** | 不影响工期与架构，新增工作量 ≤ 半天 | 文案调整、加一个筛选项、字段改名 | 开发负责人 | 否 | 否 | 不变，吸收进当前迭代 |
| **中改** | 影响工期但不动架构 | 新增一个功能点、砍掉一块已有功能、交互流程调整 | 需求方 + TL | 是（补充确认） | 否（方案补充说明） | 重新评估，书面更新 |
| **大改** | 影响架构，或推翻已有工作 | 换技术栈、换数据源、核心流程重做、推翻已验收部分 | 需求方负责人 + TL + 项目决策人 | 是（重新确认） | 是 | 重新排期，原工期作废 |

**「砍需求」同样是变更。** 只增不减的变更流程迟早会逼出一套地下流程。

## 第三步：按级别处理

### 小改

1. 记入变更记录（一句话即可）
2. 实现 + 自测，随当前提交交付
3. 更新需求文档对应段落

### 中改

1. **停止当前改动，先评估**——不许边评估边开工
2. 出影响评估：改哪些模块、工期变化、风险
3. 需求方书面确认（聊天记录留痕 + 更新需求文档）
4. 更新工期与验收标准
5. 变更记录登记，通知所有受影响方

### 大改

1. **立即停止现有工作**，保护已完成部分（能提交的先提交）
2. 回到 Step 1 需求确认，重新走一遍
3. 重新出技术方案，重新评审
4. 重新排期，旧计划标记作废
5. 已完成的投入**明确记账**（不是白干的，也不是沉没成本，写进变更记录）
6. 变更记录登记 + 同步全部干系人

## 变更留痕

每一条变更必须记录，**口头变更一律不算数**：

```markdown
## 变更记录 CR-007

| 字段 | 内容 |
|---|---|
| 变更编号 | CR-007 |
| 提出人 | @产品-张三 |
| 提出时间 | 2026-10-27 15:20 |
| 关联需求 | REQ-012 订单导出 |
| 变更内容 | 导出格式从仅 CSV 增加 Excel（.xlsx） |
| 原约定 | 需求文档 v1.2「导出支持 CSV」 |
| 变更原因 | 客户要求可直接编辑的格式 |
| 级别 | 中改 |
| 影响评估 | 新增依赖 openpyxl；导出模块 +2 人日；工期 10-31 → 11-02 |
| 审批人 | @产品负责人、@TL |
| 审批结论 | 同意，工期顺延至 11-02 |
| 验收标准变化 | 新增「导出 xlsx 可被 Excel 正常打开，列宽自适应」 |
| 状态 | 已评估 → 已批准 → 已实现 → 已验收 |
```

必填字段：**编号、提出人、时间、原约定、变更内容、原因、级别、影响评估、审批人、结论、验收标准变化、状态。**
缺「原约定」和「影响评估」的变更记录等于没记——事后无法复盘为什么变了、代价是什么。

## 红线（防范围蔓延）

| 红线 | 说明 |
|---|---|
| **口头变更不算数** | 群里一句话、会上口头答应，都不开工，补记录再说 |
| **未评估不许开工** | 影响评估出来之前，代码一个字都不改 |
| **没有审批人的变更无效** | 谁都能提，但不是谁都能批 |
| **不接受「先做做看」** | 做出来就等于承诺了，评估必须在做之前 |
| **不接受追溯性变更** | 交付完成后才说「我当时想要的是 X」，按新需求走，不追认 |
| **工期只增不口头承诺** | 任何工期变化必须落到书面计划，不接受「应该差不多」 |
| **同一需求累计小改 ≥ 3 次** | 升级为中改处理，重新确认一次整体需求 |

**范围蔓延的典型轨迹**：一次「顺便加一下」→ 一次「这个应该很简单吧」→ 一次「之前理解错了」→ 工期翻倍，没人知道是从哪一步开始歪的。

## 判定决策表

| 情况 | 判定 | 动作 |
|---|---|---|
| 需求文档已写明，只是没细述 | 澄清 | 直接做，无需登记 |
| 新增原需求没有的功能点，≤ 半天 | 小改 | 负责人批，登记，工期不变 |
| 新增功能点，> 半天，不动架构 | 中改 | 需求方+TL 批，补确认，重算工期 |
| 砍掉已确认的功能 | 中改 | 同上（减少也要记） |
| 改交互流程但不动数据结构 | 中改 | 同上 |
| 改数据结构 / 换技术栈 / 换依赖 | 大改 | 重走需求确认 + 重出方案 + 重排期 |
| 推翻已交付并验收的部分 | 大改 | 同上，已完成投入记账 |
| 无法判断属于哪级 | 按高一级 | 先评估，评估后可降级 |
| 口头提出的变更 | 待补记录 | 补齐书面记录后按级别处理 |
| 交付完成后提出的「其实我想要…」 | 新需求 | 另开需求单，不追认为变更 |

## 反模式

| 反模式 | 后果 |
|---|---|
| 「小改一下，不用走流程」 | 三次小改后工期失控，且无据可查 |
| 边评估边开工 | 评估结论是「不改」时，已写的代码变成沉没成本 |
| 变更只在聊天里说 | 事后无人认账，验收标准对不上 |
| 只记录增加，不记录删减 | 实际范围缩小了，工期却没减 |
| 谁催得急就先做谁的变更 | 优先级由嗓门决定，计划失效 |
| 大改硬当中改处理 | 架构问题被工期掩盖，上线才暴露 |
| 变更记录没有状态跟踪 | 批了但没做、做了但没验收，无人知晓 |
